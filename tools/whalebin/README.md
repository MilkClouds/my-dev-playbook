# whalebin

`pixi global install` / `uv tool install` for docker images, via [Charliecloud](https://charliecloud.io/latest/index.html).

Given a docker image with one or more useful binaries inside (e.g. `texlive/texlive:latest-full` contains `latexmk`, `pdflatex`, `latexindent`, ...), `whalebin install` exposes those binaries to your `PATH` as thin wrapper scripts. Typing `latexmk file.tex` on the host transparently runs `latexmk` inside the container as you (host UID), with `$HOME`, `$PWD`, and `/tmp` bound at the same paths, so file ownership and absolute path references just work.

## Install

Prerequisite: `charliecloud` on PATH:

```sh
pixi global install charliecloud
```

Then whalebin itself.

Remote (zero-setup, anywhere):

```sh
uv tool install --from "git+https://github.com/MilkClouds/my-dev-playbook.git#subdirectory=tools/whalebin" whalebin
```

Local (when iterating on whalebin itself):

```sh
uv tool install --from ~/GitHub/my-dev-playbook/tools/whalebin whalebin
# add --reinstall after edits to pick up changes
```

Upgrade / uninstall the tool itself follows the standard `uv tool` flow:

```sh
uv tool upgrade whalebin
uv tool uninstall whalebin
```

## Use

```sh
# Expose TeX Live binaries from the official docker image.
# --mount /mnt:/mnt is for HPC clusters where files are referenced by absolute
# path in NFS trees outside $HOME and $PWD (skip on personal Linux/macOS).
whalebin install texlive \
    --image texlive/texlive:latest-full \
    --bin latexmk,pdflatex,xelatex,lualatex,latexindent,chktex,bibtex,biber,makeindex,latexpand \
    --mount /mnt:/mnt

# Now host PATH has them; they transparently invoke ch-run
latexmk -pdf paper.tex
latexindent -w paper.tex

whalebin list                  # all envs (add --json for machine-readable)
whalebin info texlive          # single env + missing-wrapper diagnostics
whalebin upgrade texlive       # re-pull this env's image
whalebin upgrade --all         # batch re-pull every env's image
whalebin sync                  # regenerate wrappers from manifest

# Per-binary edits without uninstall+install
whalebin expose add texlive lualatex
whalebin expose remove texlive lualatex

# Edit the manifest directly (e.g., tweak mounts) — validates TOML on save
whalebin edit                  # opens $EDITOR; run `whalebin sync` after

# One-off run without a permanent wrapper (like `uv tool run`)
whalebin run texlive latexmk --version

whalebin uninstall texlive     # drop wrappers (--purge to also delete the image)
```

On first `install`, whalebin imports the image from your local docker daemon (fast, via `ch-convert`) if it's already there; otherwise it falls back to `ch-image pull` from the registry.

## How a wrapper looks

```bash
#!/usr/bin/env bash
# generated by whalebin (env: texlive, image: texlive/texlive:latest-full)
: "${CH_IMAGE_STORAGE:=$HOME/.cache/charliecloud}"
export CH_IMAGE_STORAGE
binds=(--bind "$HOME")
case "$PWD" in
    /|"$HOME"|"$HOME"/*|/tmp|/tmp/*) ;;
    *) binds+=(--bind "$PWD") ;;
esac
exec ch-run \
    --write-fake \
    --unset-env=PATH --set-env="PATH=/usr/local/bin:/usr/bin:/bin" \
    --cd "$PWD" \
    "${binds[@]}" \
    --bind /mnt:/mnt \
    texlive/texlive:latest-full -- \
    latexmk "$@"
```

- Charliecloud binds only `/tmp` (plus `/etc/passwd` and similar) by default, so the wrapper binds `$HOME`, and `$PWD` when it lies outside `$HOME` and `/tmp`, at the same paths. `--cd "$PWD"` keeps the caller's directory.
- A bind target must already exist in the image. `--write-fake` overlays a tmpfs on the image so `ch-run` can create those targets, including `--mount` destinations; the stored image is never modified. It needs unprivileged overlayfs (Linux 5.11 or later).
- `--unset-env=PATH --set-env=...` makes the container pick its own `latexmk` instead of finding *this wrapper* through the host `$PATH`, which Charliecloud passes through.
- `whalebin run` executes this same script, so ad-hoc runs and installed wrappers behave identically.

## Files

- Manifest: `~/.config/whalebin/manifest.toml`
- Wrappers: `~/.local/bin/` (override with `$WHALEBIN_BIN`)
- Image storage: managed by Charliecloud (default `/var/tmp/<user>.ch`, node-local)

## Why Charliecloud (not docker, not singularity, not whalebrew)?

- **Docker**: requires daemon + explicit `-v` mounts for every path, hardcoded `--user` UID, doesn't fit "portable container-as-CLI" semantics.
- **Singularity**: works (`$HOME` auto-mount + host-user model), but heavier and typically requires a system-wide (root) install, whereas charliecloud installs user-space via `pixi global install charliecloud`.
- **[whalebrew](https://github.com/whalebrew/whalebrew)**: targets single-binary, whalebrew-aware images and mounts only `$PWD` as `/workdir`. Multi-binary images like `texlive/texlive`, absolute path references, and cluster NFS mounts don't fit cleanly.

Charliecloud's defaults (rootless via user namespaces, host fs largely visible, single static binary distribution) match the "isolated env + exposed binary surface" pattern that pixi global / uv tool already use, just with a docker image as the env.
